# シナリオ② システム開発：開発依頼 → 納品

**出典：** 実際のヒアリング（シミュレーションではない）
**話し手：** システム開発会社側の担当者
**描いたもの：** 現状フロー（AS-IS）
**規模：** 3役割 × 15列 / 25ステップ

## この業務は何か

顧客からのデジタル化・システム化の相談を受け、現状分析と課題整理を経て、
要件・課題整理（第1回）とシステム開発（第2回）の**2段階の発注**で進め、納品までを行う流れ。

**2段階発注が特徴：**

- **第1回** … 要件の整理と課題の整理。現状業務や課題を顧客と認識合わせし、成果物として提出する
- **第2回** … 整理した要件・課題・実現したいフローをもとに機能を開発する

第1回の見積もりを判断する時点では、**顧客はシステム開発まで行うかを決める必要がない**。
まず「要件・課題整理をやるか」だけを判断する。

## 範囲

- **始まり：** 顧客からの開発依頼（デジタル化・システム化の相談）
- **終わり：** 納品完了／または見送りによる終了

## 登場する役割

| 役割 | 区分 | 担当する範囲 |
|------|------|------------|
| 顧客 | 社外 | 相談、各判断（第1回発注・第2回発注・検収） |
| 上流工程担当 | 社内 | 現状分析〜成果物合意、見積もりの提示、再提案 |
| 開発担当 | 社内（会社全体） | システム開発、納品 |

## このシナリオで使っている記法

- **条件分岐（`cond`）** … 第1回を発注するか／システム化に進むか／再提案でも合意しないか
- **例外分岐（`except`）** … 実業務で運用できるか（できなければ開発へ戻る）
- **戻り** … 発注NG時は見積もりへ戻って再提案。検収NG時は開発へ戻ってやり直し
- **待ち（`wait`）** … 顧客の判断待ちが3か所
- **成果物（`artifact` / `op`）** … 見積書／途中成果物／現状業務フロー・理想業務フロー・課題マッピング
- **マイルストーン** … 第1回発注・第2回発注・納品

**使っていないもの：** 所要時間・頻度・課題（⚠）・改善案（TO-BE）・手段・用語補足。
ヒアリングで「まちまち」「特になし」との回答だったか、そもそも伺えていないため、
**推測で埋めず空欄**にしている（`flow-interview` の鉄則）。空欄の一覧は `ヒアリング時の会話.md` の末尾。

## 記法検証で分かったこと（このシナリオでの発見）

| 発見 | 内容 | 回避方法 |
|------|------|---------|
| **end/start に `id` が無い** | 分岐の `then:` から終了ノードを参照できない。参照はラベルで行うしかなく、**同じラベルの終了が複数あると指せない** | 終了のラベルを一意にした（「終了（第1回見送り）」「終了（第2回見送り）」） |
| **成果物が複数書けない** | 1ステップに `artifact` は1つ。成果物合意では3つ同時に出る | 3つを1行に併記した |
| **枝が「戻り」であることを示せない** | 条件分岐の枝が前の工程に向かう（見積もりへ戻る・開発へ戻る）場合、記法上は通常の遷移と区別がつかない | 図では手戻りと同じ赤い破線で描き、生成物に注記した |
| **補足・注記を書く場所が無い** | 「この時点では開発まで判断しなくてよい」のような重要な補足を記法に書けない | この概要ファイルに記載した |

## 逆流チェック（`flow-verify`）の結果

- **検査B（根拠）** … 全34フィールド。**会話に根拠のない記述は0件**（一致しなかった17件はすべて発言の言い換え）
  - ただし1件の**取りこぼし**を発見し修正した（「時には社内風土まで踏み込んで」が業務改善検討の行為から落ちていた）
- **検査A（到達）** … `.flow` の全項目が図に**完全一致**で出ている（切り詰め0・省略0）
- **検査C（描画）** … ノード・チップ・ラベルの重なり0。分岐前後の矢印は21px確保。
  枝が交差する箇所（発注判断）は、ラベルを**到達先の近く**に置いて取り違えを防いだ
