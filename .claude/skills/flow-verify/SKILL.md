# flow-verify — 業務フロー成果物の逆流チェック

**ヒアリング記録 ⇄ `.flow` ⇄ 生成HTML** の3つが食い違っていないかを検証する。
この検証は**作った本人（AI）が必ず自分で通す**。人に指摘されてから直すのでは遅い。

## なぜ必要か

AI は「もっともらしい業務の詳細」を無意識に補ってしまう。所要時間・課題・改善案・使用システムは
**それらしく書けてしまう**ため、あとから見て「聞き取った事実」と「AIの創作」を見分けられなくなる。
業務フロー図でこれが起きると、**存在しない課題をもとに改善が進む**。最も避けたい壊れ方である。

## 検査する3方向

### 検査A：会話 → `.flow` → 図（届いているか）

ヒアリング記録の発言をひとつずつ拾い、`.flow` と図まで到達しているか確認する。

- 発言が `.flow` に無い → **取りこぼし**。追加する。
- `.flow` にあるのに図に無い → 省略が**注記されているか**を確認する。
  注記が無ければ、省略したこと自体が事故。注記するか、描き方を変えて載せる。
- **文字が途中で切られていないか**を必ず見る。`.flow` の値と図の文字列を突き合わせ、
  部分一致で終わっているものは「切り詰め」＝事故として扱う（`docs/SPEC.md §5.7`）。

### 検査B：`.flow` → 会話（根拠があるか）★ 最重要

`.flow` の**全フィールドを機械的に列挙**し、それぞれ会話のどの発言に対応するかを示す。

対応が示せないものは、次のどれかに必ず分類する：

| 分類 | 扱い |
|------|------|
| **言い換え** | 会話の内容を別の語で書いただけ。そのままでよい（対応する発言を挙げられること） |
| **推測** | 会話から妥当に導けるが、本人は言っていない。値に `（推測）` を付け、記録の「推測で補った箇所」に列挙する |
| **創作** | 会話に根拠が無い。**削除する。** 残したいなら、聞き直して事実にする |

**特に疑ってかかるフィールド：** `time` / `freq`（数値は創作されやすい）、`issue`（もっともらしい課題）、
`tobe`（ありがちな改善案）、`by` の手段名（実在しないシステム名）。

### 検査C：図の描画（読めるか）

生成HTMLを**実際に開いて目で見る**。座標計算だけで済ませない。

- 矢印が**文字を貫通**していないか（線とテキストの重なり）
- 分岐ラベルが**枝の向きと一致**しているか（`docs/SPEC.md §5.6`）。左へ抜ける枝のラベルが右側に無いか
- ★マイルストーンが**どのノードの節目か一意に読めるか**（2つのノードの中間に浮いていないか）
- ノード・チップ・ピル・ラベルが重なっていないか
- 図中に英語の専門語（`fork` / `join: all` 等）が出ていないか（`docs/SPEC.md §5.5`）
- 用語（`[[...]]`）が点線下線で表示され、説明が出るか。`[[` `]]` が素通しで残っていないか

## 進め方

1. 3ファイルを読む（ヒアリング記録・`.flow`・生成HTML）。
2. **検査B を最初にやる。** 影響が最も大きい。`.flow` の全フィールドを表にして、
   「対応する発言」「分類（言い換え/推測/創作）」を1行ずつ埋める。
3. 検査A で取りこぼしと切り詰めを洗う。
4. 検査C はブラウザで開いて確認する。可能ならスクリーンショットを撮り、**目で見て**判断する。
5. 結果を表で報告する。**問題が無い場合も「何件中何件を確認した」と件数を示す**（黙って合格にしない）。

## 報告の型

```
## 逆流チェック結果

### 検査B：.flow の根拠（最重要）
| 箇所 | 値 | 対応する発言 | 分類 |
|------|----|-----------|------|
| ... | ... | 「〜」 | 言い換え |
| ... | ... | なし | 創作 → 削除 |

### 検査A：会話 → 図 の到達
{n} 項目中 {m} 件が図に到達。未到達 {k} 件（注記の有無）

### 検査C：描画
{確認した観点と結果}
```

## やってはいけないこと

- 「たぶん合っている」で済ませる。**必ず全フィールドを列挙**する。
- 創作を「推測」と言い換えて残す。根拠が無いものは推測ではなく創作。
- 図を開かずに座標計算だけで描画を合格にする。
