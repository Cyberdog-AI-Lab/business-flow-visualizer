# flow-interview — 業務ヒアリング → .flow 生成

担当者に質問しながら業務フローを聞き取り、**`.flow`（YAML）** に構造化する。
記法の語彙・書式は必ず `docs/SPEC.md` を正とする。

## スタンス

- 一度に全部聞かない。**骨格（役割・時系列・主要ステップ）→ 肉付け（手段・成果物・待ち・課題）→ 分岐/並行/例外** の順で会話を小さく回す。
- 埋まらない項目は空欄でよい。**まずドラフトを出し**、そこから相手に直してもらう。
- 相手の言葉・ニュアンスを変えない。推測で補ったところは「（推測）」と添える。

## ヒアリングの順序

### 1. 全体像

- この業務の**目的**と**範囲**（どこから始まり、どこで終わるか）。
- 描くのは **AS-IS（現状）** か **TO-BE（理想）** か。

### 2. 役割（roles＝行）

- 登場する**部署・役職・社外**を洗い出す。社外/外部は `#社外` `#外部` を付ける。
- 上から並べる順（だいたい主担当→下流）。

### 3. 時系列（timeline＝列）＋マイルストーン

- 時間の刻み（`Day0..` `月初/月末` `営業日` `年月日`）。
- 節目（`★確定` `★承認` `★実行` 等）を `milestones` に。

### 4. ステップを時系列で聞く（各行為ごとに）

1つの行為につき、次を順に埋める：

- **誰が・何をするか** → `act`＋`at:[役割, 時点]`
- **手段** → `by: <人手|システム|外部>/<手段名>`（自動化候補の見極めに重要）
- **成果物と操作** → `artifact` ＋ `op`（例：請求DB／レコード登録）
- **所要時間・頻度** → `time` / `freq`（改善ROIの根拠）
- **待ち・滞留** → `wait`（承認待ち等。改善の主戦場なので必ず聞く）
- **困りごと** → `issue`（課題）

### 5. 分岐・並行・手戻り・期限

- **条件で分かれる**か → `cond`（`yes`/`no` or `case`）。
- **正常系から外れる**分岐（失敗・却下）→ `except`（`ng`/`ok`）。
- **同時並行**で走る作業があるか → `par`（fork）＋合流は `join: all|any`。
- **やり直し・差戻し**があるか → `rework: <戻り先>`。
- **期限・SLA**があるか → `sla`、超過時の動き → `on_overdue`。

### 6. 出力

- `docs/SPEC.md` に沿った `.flow`（YAML）を書き出す。`examples/*.flow` を書式の手本にする。
- 埋まらなかった項目・推測箇所を短く添える。
- 最後に「**`flow-visualize` でHTML図にしますか？**」と提案する。

## 聞き方のコツ

- 「その作業、Excelですか？システムですか？外部（他社・API）ですか？」→ `by` の区分が即埋まる。
- 「次の人に渡してから、どれくらい待ちますか？」→ `wait` が拾える。
- 「うまくいかない時は？」→ `except` / `rework` が拾える。
- 「それ、他の作業と同時に走ってますか？」→ `par` / `join` が拾える。
